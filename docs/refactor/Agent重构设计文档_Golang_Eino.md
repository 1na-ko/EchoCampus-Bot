## 第一章 概述与背景分析

### 1.1 重构背景与动机

#### 1.1.1 业务发展需求

EchoCampus-Bot 智能校园问答系统自上线以来，已成功服务于校园信息查询场景，基于 RAG（Retrieval-Augmented Generation）技术实现了知识库问答功能。然而，随着业务发展和技术演进，原有系统架构面临以下挑战：

**团队技术栈统一需求**

当前团队主要技术栈为 Golang，已有多个基于 Golang 开发的校园小程序后端服务稳定运行。原 Java 技术栈的 EchoCampus-Bot 系统在以下方面带来了额外的维护成本：

- 开发人员需要维护两套技术栈的知识体系
- 代码复用困难，无法共享已有的 Golang 基础设施和工具库
- 部署运维需要维护不同的 CI/CD 流程和监控体系
- 新成员上手成本增加

**智能体能力升级需求**

原系统基于 RAG 架构，主要实现知识检索增强生成能力。随着大语言模型和 Agent 技术的快速发展，业务侧提出了更高的智能化需求：

- **多步骤任务规划**：支持复杂校园事务的多步骤处理（如选课推荐、活动报名流程指引）
- **工具调用能力增强**：集成更多校园服务接口（成绩查询、课表获取、图书馆座位预约等）
- **记忆管理优化**：支持长期用户偏好记忆和上下文理解
- **多 Agent 协作**：未来支持多个专业 Agent 协同处理复杂任务

**系统对接需求**

校园小程序后端服务（基于 Golang）需要调用智能问答能力，当前跨语言调用带来的问题：

- RPC/HTTP 调用增加网络延迟和序列化开销
- 数据模型需要额外转换层
- 事务一致性难以保证
- 认证授权需要额外适配

#### 1.1.2 技术演进驱动

**向量存储架构简化**

原系统采用 PostgreSQL + Milvus 的双数据库架构：
- PostgreSQL：存储业务数据（用户、会话、知识库元数据）
- Milvus：存储向量数据，支持相似度检索

这种架构虽然在向量检索性能上有优势，但也带来了额外的复杂性：
- 数据一致性维护成本（两个数据库的事务协调）
- 运维复杂度增加（Milvus 依赖 etcd、MinIO 等组件）
- 资源占用较高（内存敏感型应用）

PostgreSQL 的 pgvector 扩展已经成熟，对于当前业务规模（万级文档量）完全能够满足需求，且具有以下优势：
- 统一数据存储，简化架构
- 原生事务支持，保证数据一致性
- 运维成本大幅降低
- 与现有 PostgreSQL 基础设施复用

**Eino 框架生态成熟**

字节跳动开源的 Eino 框架专为 Golang 生态设计，提供了完整的 AI 应用开发能力：
- 支持多种 LLM 提供商（OpenAI、DeepSeek、阿里云等）
- 内置 Agent、RAG、Tool Calling 等核心能力
- 流式处理和异步编排支持
- 完善的可观测性和监控

#### 1.2.3 核心业务流程

**RAG 问答流程**（当前实现）：

```
用户提问 → JWT认证 → 问题预处理
    ↓
[EnhancedRagService] AI自主判断是否检索
    ↓
(需要检索) → EmbeddingService 问题向量化
    ↓
MilvusService 向量相似度检索
    ↓
KnowledgeSearchTool 格式化检索结果
    ↓
EnhancedLlmService 构建Prompt + 调用LLM
    ↓
ChatService 保存对话历史
    ↓
流式/非流式响应返回
```

**知识库处理流程**：

```
文档上传 → 类型校验 → 文件存储
    ↓
DocumentProcessService 异步处理
    ↓
DocumentParserFactory 选择解析器
    ↓
TextChunkService 智能文本切块
    ↓
EmbeddingService 批量向量化
    ↓
MilvusService 存储向量 + PostgreSQL 存储元数据
```

### 1.3 重构目标与范围

#### 1.3.1 核心目标

| 目标编号 | 目标描述 | 优先级 | 验收标准 |
|---------|---------|-------|---------|
| G1 | 技术栈统一为 Golang | P0 | 全部业务逻辑使用 Golang 实现 |

| G5 | 支持与校园小程序后端无缝对接 | P1 | 提供内部 RPC 接口和认证机制 |

#### 1.3.2 重构范围

**在范围内（In Scope）**：

- 后端服务完整重构（Golang + Eino）

- Agent 能力增强设计
- 与校园小程序后端对接接口设计
- 测试用例迁移和补充

**不在范围内（Out of Scope）**：

- 前端代码重构（保持 Vue.js 技术栈）
- 新增业务功能开发（聚焦技术重构）
- 历史数据清洗和治理
- 第三方 AI 服务提供商切换

## 第二章 技术栈选型与依据

### 2.1 Golang 语言选型分析

#### 2.1.1 选型理由

**团队技术栈统一**

| 维度 | Java (现状) | Golang (目标) |
|------|------------|---------------|
| 团队熟悉度 | 部分成员熟悉 | 全员熟悉 |
| 现有项目数 | 1个 (EchoCampus-Bot) | 多个校园小程序后端 |
| 代码复用性 | 无法与现有服务复用 | 可复用认证、配置、监控等模块 |
| 运维一致性 | 需独立部署流程 | 与现有服务统一部署 |

**语言特性优势**

- **高性能并发**：Goroutine + Channel 原生支持高并发场景，对于流式响应、异步文档处理等场景具有天然优势
- **编译型语言**：编译后为单一二进制文件，部署简单，启动速度快（对比 JVM 冷启动）
- **内存效率**：无 GC 停顿问题的内存管理，适合对延迟敏感的 AI 应用
- **简洁语法**：强制代码风格统一，降低团队协作成本

**生态系统支持**

| 领域 | Golang 生态组件 | 说明 |
|------|----------------|------|
| Web 框架 | Gin / Echo / Fiber | 高性能 HTTP 框架 |
| ORM | GORM / Ent | 数据库访问 |
| AI 框架 | Eino | 字节跳动开源的 LLM 应用框架 |
| 配置管理 | Viper | 多格式配置支持 |
| 日志 | Zap / Zerolog | 结构化日志 |
| 监控 | Prometheus Client | 指标采集 |

#### 2.1.2 Java 与 Golang 对比分析

| 对比维度 | Java (Spring Boot) | Golang | 重构影响评估 |
|---------|-------------------|--------|-------------|
| **启动时间** | 5-15秒 | <1秒 | 开发效率提升，部署更快 |
| **内存占用** | 200-500MB (JVM) | 20-50MB | 资源成本显著降低 |
| **并发模型** | 线程池 | Goroutine | 流式响应实现更简洁 |
| **错误处理** | 异常机制 | 返回值 | 需要适应显式错误处理 |
| **依赖管理** | Maven/Gradle | Go Modules | 更简洁的依赖管理 |
| **构建产物** | JAR + JVM | 单一二进制 | 部署和分发更简单 |
| **热更新** | 支持（开发环境） | 编译重启 | 开发体验略有变化 |

### 2.2 Eino 框架深度解析

#### 2.2.1 框架概述

Eino（字节跳动开源）是专为 Golang 设计的 AI 应用开发框架，提供了构建 LLM 应用的完整能力栈。选择 Eino 的核心理由：

**原生 Golang 支持**
- 无需跨语言调用，避免 CGO 或 FFI 带来的复杂性
- 充分利用 Golang 的并发优势
- 与 Golang 生态无缝集成

**完整的 Agent 能力**
- 内置 ReAct Agent 实现
- 支持 Tool Calling（函数调用）
- 多 Agent 编排能力
- 流式输出原生支持

**多模型支持**
- OpenAI / Azure OpenAI
- 阿里云通义千问
- DeepSeek
- 自定义模型适配

#### 2.2.2 核心组件映射

| 原 Java 组件 (LangChain4j) | Eino 对应组件 | 功能说明 |
|---------------------------|--------------|---------|
| `ChatLanguageModel` | `model.ChatModel` | LLM 调用接口 |
| `EmbeddingModel` | `model.Embedder` | 向量化接口 |
| `DocumentSplitter` | `indexer.Splitter` | 文本切块 |
| `EmbeddingStore` | `retriever.VectorStore` | 向量存储 |
| `ContentRetriever` | `retriever.Retriever` | 检索器 |
| `Tool` / `@Tool` | `tool.Tool` | 工具定义 |
| `AiService` | `agent.Agent` | Agent 编排 |

### 2.3 PostgreSQL + pgvector 向量存储方案

#### 2.3.1 pgvector 技术特性

pgvector 是 PostgreSQL 的向量相似度搜索扩展，支持：

- **向量类型**：`vector(n)` 类型，支持最高 16000 维向量
- **索引类型**：
  - IVFFlat：适合中等规模数据，构建快
  - HNSW：适合大规模数据，查询快
- **距离函数**：
  - `<->` L2 距离
  - `<#>` 内积（负值）
  - `<=>` 余弦距离

#### 2.3.2 架构对比：Milvus vs pgvector

| 对比维度 | Milvus (原方案) | pgvector (新方案) |
|---------|----------------|-------------------|
| **部署复杂度** | 高（需 etcd、MinIO） | 低（PostgreSQL 扩展） |
| **运维成本** | 高（独立组件维护） | 低（与业务数据库统一） |
| **事务支持** | 不支持 | 完整 ACID 支持 |
| **数据一致性** | 最终一致性 | 强一致性 |
| **检索性能** | 优秀（大规模场景） | 良好（万级规模足够） |
| **功能丰富度** | 高（专业向量数据库） | 中（核心功能完备） |
| **生态集成** | 需要额外适配 | 原生 SQL 支持 |

#### 2.3.3 pgvector 索引策略设计

针对本项目知识库场景（预估 10,000-50,000 文档片段），推荐索引配置：

```sql
-- HNSW 索引（推荐，查询性能更好）
CREATE INDEX ON knowledge_vectors 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 查询时设置 ef_search 参数
SET hnsw.ef_search = 100;
```

**索引参数说明**：

| 参数 | 值 | 说明 |
|------|-----|------|
| m | 16 | 每层连接数，影响查询精度和内存 |
| ef_construction | 64 | 构建时搜索宽度，影响索引质量 |
| ef_search | 100 | 查询时搜索宽度，影响查询精度和速度 |

// internal/agent/tools/knowledge_search.go

type KnowledgeSearchTool struct {
    knowledgeService knowledge.KnowledgeService
    defaultTopK      int
    defaultThreshold float32
}

func (t *KnowledgeSearchTool) Name() string {
    return "knowledge_search"
}

func (t *KnowledgeSearchTool) Description() string {
    return "在校园知识库中搜索相关信息。当用户询问关于学校、课程、活动、设施等校园相关问题时，使用此工具获取准确的知识库信息。"
}

func (t *KnowledgeSearchTool) Parameters() map[string]ParameterDef {
    return map[string]ParameterDef{
        "query": {
            Type:        "string",
            Description: "要搜索的问题或关键词",
            Required:    true,
        },
        "top_k": {
            Type:        "number",
            Description: "返回结果数量，默认5",
            Required:    false,
        },
        "category": {
            Type:        "string",
            Description: "知识分类过滤",
            Required:    false,
        },
    }
}

func (t *KnowledgeSearchTool) Execute(ctx context.Context, args map[string]interface{}) (interface{}, error) {
    query, _ := args["query"].(string)
    topK := t.defaultTopK
    if v, ok := args["top_k"].(float64); ok {
        topK = int(v)
    }
    
    opts := &knowledge.SearchOptions{
        TopK:      topK,
        Threshold: t.defaultThreshold,
    }
    
    if category, ok := args["category"].(string); ok && category != "" {
        opts.Categories = []string{category}
    }
    
    results, err := t.knowledgeService.Search(ctx, query, opts)
    if err != nil {
        return nil, err
    }
    
    return t.formatResults(results), nil
}
```

// internal/repository/vector.go

type VectorRepository interface {
    // 插入向量
    Insert(ctx context.Context, vector *KnowledgeVector) error
    InsertBatch(ctx context.Context, vectors []*KnowledgeVector) error
    
    // 相似度搜索
    Search(ctx context.Context, embedding []float32, opts *SearchOptions) ([]SearchResult, error)
    
    // 删除
    DeleteByChunkID(ctx context.Context, chunkID int64) error
    DeleteByDocID(ctx context.Context, docID int64) error
    
    // 统计
    Count(ctx context.Context) (int64, error)
}

// SearchOptions 搜索选项
type SearchOptions struct {
    TopK       int
    Threshold  float32
    Categories []string
    DocIDs     []int64
}

// 相似度搜索 SQL
const searchSQL = `
    SELECT 
        kv.id,
        kv.chunk_id,
        kv.doc_id,
        kc.content,
        kd.title AS doc_title,
        kv.category,
        1 - (kv.embedding <=> $1::vector) AS score
    FROM knowledge_vectors kv
    JOIN knowledge_chunks kc ON kv.chunk_id = kc.id
    JOIN knowledge_docs kd ON kv.doc_id = kd.id
    WHERE 1 - (kv.embedding <=> $1::vector) >= $2
    %s
    ORDER BY kv.embedding <=> $1::vector
    LIMIT $3
`
```

type MigrationTask struct {
    milvusClient milvus.Client
    pgDB         *gorm.DB
    batchSize    int
    logger       *zap.Logger
}

func (t *MigrationTask) Execute(ctx context.Context) error {
    // 1. 获取 Milvus 中的总记录数
    count, err := t.milvusClient.GetCollectionStatistics(ctx, collectionName)
    if err != nil {
        return err
    }
    t.logger.Info("开始迁移", zap.Int64("total_records", count))
    
    // 2. 分批读取和写入
    var offset int64 = 0
    for offset < count {
        // 从 Milvus 读取
        records, err := t.readFromMilvus(ctx, offset, t.batchSize)
        if err != nil {
            return err
        }
        
        // 转换并写入 pgvector
        if err := t.writeToPgvector(ctx, records); err != nil {
            return err
        }
        
        offset += int64(len(records))
        t.logger.Info("迁移进度", zap.Int64("completed", offset), zap.Int64("total", count))
    }
    
    // 3. 验证
    return t.verify(ctx)
}

#### 7.2.1 线程模型 vs Goroutine

| 特性 | Java 线程 | Go Goroutine |
|-----|----------|--------------|

public SseEmitter streamChat(@RequestBody ChatRequest request) {

```go
// Go: SSE with Gin
func (h *ChatHandler) StreamChat(c *gin.Context) {
    var req dto.ChatRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(400, response.Error(err))
        return
    }
    
    // 设置 SSE headers
    c.Header("Content-Type", "text/event-stream")
    c.Header("Cache-Control", "no-cache")
    c.Header("Connection", "keep-alive")
    
    // 获取 flusher
    flusher, ok := c.Writer.(http.Flusher)
    if !ok {
        c.JSON(500, response.Error(errors.New("streaming not supported")))
        return
    }
    
    // 创建 context 用于取消
    ctx, cancel := context.WithCancel(c.Request.Context())
    defer cancel()
    
    // 监听客户端断开
    go func() {
        <-c.Request.Context().Done()
        cancel()
    }()
    
    // 流式处理
    err := h.agentSvc.ChatStream(ctx, &req, func(event *StreamEvent) {
        data, _ := json.Marshal(event)
        fmt.Fprintf(c.Writer, "event: %s\ndata: %s\n\n", event.Type, data)
        flusher.Flush()
    })
    
    if err != nil {
        fmt.Fprintf(c.Writer, "event: error\ndata: %s\n\n", err.Error())
        flusher.Flush()
    }
}
```

type BusinessError struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Cause   error  `json:"-"`
}

func (e *BusinessError) Error() string {
    if e.Cause != nil {
        return fmt.Sprintf("%s: %v", e.Message, e.Cause)
    }
    return e.Message
}

// 预定义错误
var (
    ErrUserNotFound     = &BusinessError{Code: 20004, Message: "用户不存在"}
    ErrInvalidPassword  = &BusinessError{Code: 20003, Message: "密码错误"}
    ErrDocNotFound      = &BusinessError{Code: 30003, Message: "文档不存在"}
    ErrUnsupportedFile  = &BusinessError{Code: 30001, Message: "不支持的文件类型"}
)

// 包装错误
func Wrap(err error, code int, message string) error {
    return &BusinessError{Code: code, Message: message, Cause: err}
}

### 8.1 重构策略选择

#### 8.1.1 策略对比

| 策略 | 优点 | 缺点 | 适用场景 |
|-----|------|------|---------|
| **绞杀者模式** | 风险可控，可渐进式 | 需要维护两套系统 | 大型系统 |
| **完全重写** | 技术债务清零 | 风险高，周期长 | 小型系统 |
| **模块迁移** | 灵活，可验证 | 集成复杂 | 中型系统 |

**决策：采用模块迁移策略**

考虑到本项目规模适中，且需要保证业务连续性，采用模块迁移策略：
1. 优先迁移核心模块（Agent、知识库）
2. 逐步迁移辅助模块（用户、系统）
3. 最后切换网关路由

| 数据迁移丢失 | 低 | 高 | 完整备份、分批迁移、验证脚本 |
| 团队 Go 经验不足 | 中 | 中 | 技术培训、Code Review |

### 10.2 进度风险

| 风险项 | 可能性 | 影响 | 应对措施 |
|-------|-------|------|---------|
| 需求变更 | 中 | 中 | 明确重构范围，变更走流程 |
| 人员变动 | 低 | 高 | 知识文档化，代码规范化 |
| 依赖外部服务 | 中 | 中 | 提前对接，预留 buffer |
| 测试周期不足 | 中 | 中 | 自动化测试，并行执行 |

### 10.3 回滚方案设计

#### 10.3.1 回滚触发条件

| 级别 | 条件 | 决策人 |
|-----|------|--------|
| P0 | 核心功能不可用超过 30 分钟 | 技术负责人 |
| P1 | 性能下降超过 50% | 技术负责人 |
| P2 | 非核心功能异常 | 开发负责人 |

#### 10.3.2 回滚流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        回滚执行流程                                     │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. 触发回滚决策                                                        │
│     │                                                                   │
│     ▼                                                                   │
│  2. 通知相关人员 (钉钉/企微群组)                                        │
│     │                                                                   │
│     ▼                                                                   │
│  3. 网关流量切回旧系统                                                  │
│     │                                                                   │
│     ▼                                                                   │
│  4. 验证旧系统正常                                                      │
│     │                                                                   │
│     ▼                                                                   │
│  5. 保留新系统日志和数据用于分析                                        │
│     │                                                                   │
│     ▼                                                                   │
│  6. 问题分析和修复                                                      │
│     │                                                                   │
│     ▼                                                                   │
│  7. 制定重新上线计划                                                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 10.3.3 数据回滚策略

| 场景 | 策略 | 说明 |
|-----|------|------|
| 数据库结构兼容 | 直接切换 | 新系统写入的数据旧系统可读 |
| 数据库结构不兼容 | 数据同步 | 将增量数据同步回旧库 |
| 向量数据 | 保留 Milvus | 迁移期间不删除 Milvus 数据 |
